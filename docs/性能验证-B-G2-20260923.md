# B-G2 性能项验证报告（2026-09-23）

> 对应 `docs/13-后端文档对齐-goal-prompt-20260923.md` §2 的 B-G2（性能优化 5 项）。
> 复现脚本：`bash scripts/explain-bg2-2026-09-23.sh`（一次性库 `textbook_explain`，可重复执行）。
> 环境：本机 Windows + MySQL 8.0.29（非生产等价，见 §5 局限说明）。

## 2. 逐项实测

数据量：`notice_record` 3 万行（1 万学生 × 3 轮，其中 1 万行已确认）、`audit_log` 3 万行（跨 30 天）、
在册学生 1 万；规模放大复核再补到 3 万学生 / 24 万 `notice_record`。
计时口径：**服务端**耗时（同一连接内 `NOW(6)` 差值，跑 5 次取最快），排除 `mysql.exe` 进程启动时间。

### 2.1 ① notice_record 的 user_id 前导索引 —— 未采纳

`/api/notice/mine` 的实际谓词（`NoticeRecordMapper#selectConfirmedByUserAndTasks`）：

```sql
SELECT * FROM notice_record
 WHERE user_id = ? AND confirmed_at IS NOT NULL AND deleted = 0 AND task_id IN (...)
```

规模放大到 **22 万行 / 20 个 task**（一个学期内的历史任务）：

| 场景 | 耗时 | EXPLAIN ANALYZE 走的索引 |
|------|------|--------------------------|
| 无 `idx_notice_user` | 1.6 ms | `idx_notice_confirm (task_id, user_id, confirmed_at)` |
| 有 `idx_notice_user` | 1.9 ms | 仍走 `idx_notice_confirm` |

单 task 场景（3 万行）：0.3 ms / 0.3 ms，同样无差异。

**判定**：既有 `idx_notice_confirm (task_id, user_id, confirmed_at)` 已完全覆盖该谓词（等值 `user_id` + `IN task_id` + `confirmed_at IS NOT NULL` 正好是该索引的最左前缀），
MySQL 优化器在两种情况下都选它。再加一个用不到的索引只带来写放大与存储开销，**故不加**。
本项与 goal prompt 的描述不一致，按「以代码实际行为为准」处理；证据留在迁移脚本注释与本报告，避免后人照文档重复加。

### 2.2 ② audit_log 的 at 前导索引 —— 采纳

`GET /api/admin/audit` 允许只按时间范围筛（`userId`/`action`/`resource` 全空）：

```sql
SELECT * FROM audit_log WHERE at >= ? AND at <= ? ORDER BY at DESC LIMIT 20
```

| 阶段 | 耗时 | EXPLAIN ANALYZE |
|------|------|-----------------|
| 迁移前 | **71.0 ms** | `Table scan on audit_log` + `Sort: at DESC`（filesort） |
| 迁移后 | **0.5 ms** | `Index range scan on audit_log using idx_audit_at ... (reverse)` |

其余三个索引（`idx_audit_user` / `idx_audit_action` / `idx_audit_resource`）都是别的列前导，无法服务「只按时间筛」这一常见形态。

### 2.3 ④ 导入预哈希范围 —— 采纳

`ImportRowWriter#hashInitialPasswords` 原先对文件内**全部** `user_no` 预哈希；已存在账号的密码并不因导入改变
（类注释：已存在用户只更新姓名/手机号），所以这部分 BCrypt 是纯浪费——单次 60-100 ms，重复导入一份全量名单（绝大多数行是已存在账号）要白付一遍。

现改为先按 `ImportRunContext#user(userNo)`（按批预取的存在性缓存）过滤，**只为本批将新建的账号**算。
单测 `ImportPasswordHashScopeTest` 覆盖四种情形：新+旧混合（只算 1 次）、全部已存在（0 次）、同一新学号重复行（去重后 1 次）、新建账号仍写入初始密码哈希。

> 效果：重复导入全量名单的 BCrypt 计算次数 **100% → 0**；首次导入（全是新账号）行为不变。

### 2.4 ⑤ 看板未确认计数 —— 采纳（口径一致，收益在查询次数与内存）

原实现（`NotifyService#countUnconfirmedTargetUsers`）把目标任务角色的**全部用户**与全部在册 profile 拉进 JVM 做集合差：
1 条任务查询 + 1 条 user_role 查询 + 1 条全量 profile 查询 + 1 条全量确认记录查询 + `USER_CHUNK=500` 分块用户查询若干，
再在内存里建 4 个 `HashSet`。现改为**单条聚合 SQL**（`NoticeRecordMapper#countUnconfirmedTargetUsers`），返回 1 行。

**口径一致性**（关键，已实测核对）：`uk_task_active (semester_id, active_flag, deleted)` 保证同学期至多 1 个 active 任务，
故「任务 × 目标角色」的匹配只需按该任务的角色码过滤；新 SQL 与旧实现返回同一数字（3 万学生场景：20000 = 30000 目标 − 10000 已确认）。

**耗时对比（如实报告，含不利数据）**：

| 规模 | 旧实现（内存集合差） | 新实现（单条聚合 SQL） |
|------|---------------------|------------------------|
| 1 万学生 / 3 万行 | 23 条 SQL、4 万行进 JVM，SQL 侧合计 **142.1 ms** | 1 条 SQL 返回 1 行，**182.1 ms** |
| 3 万学生 / 24 万行 | 3 条全量查询 124.0 ms + 60 条分块查询 0.7 ms/条 ≈ **166.0 ms**，另有 **12 万行**进 JVM | 1 条 SQL 返回 1 行，**678.9 ms** |

**判定**：**DB 侧耗时旧实现更低**（聚合 SQL 对 3 万学生做 3 万次嵌套循环查找，而旧实现是 3 次全表扫 + 分块点查）。
采纳的理由不在 DB 侧，而在：

1. **查询次数 64 → 1**（旧实现的 SQL 数随用户数线性增长：`USER_CHUNK=500` 时 3 万学生 = 60 条分块查询）；
2. **网络与内存：12 万行 → 1 行**，Java 侧成本与用户数**解耦**（O(1) 内存）；旧实现要同时持有 12 万 MyBatis 实体
   + 4 个 3 万元素 `HashSet`——**生产 JVM 堆仅 `-Xmx320m`**（见 `docs/后端测试报告-textbook-order-server-20260923.md` §1.2），
   这是实打实的 GC 压力与 OOM 风险；
3. 看板是超管低频接口，单次数百毫秒可接受；旧实现的 Java 侧成本（实体映射 + 集合运算）尚未计入上表的 SQL 耗时。

**后续可选项（本轮不做）**：若看板日后成为瓶颈，可加物化计数表或 `notice_record (task_id, confirmed_at)` 覆盖索引；
也可考虑让聚合 SQL 走哈希反连接（本轮实测 `LEFT JOIN ... IS NULL` 写法更慢，289 ms vs 235 ms，故未采用）。

## 3. 门禁与回归

- `db/migration-2026-09-23-perf.sql` 幂等（先查 `information_schema.STATISTICS`），进 `MigrationScriptTest`（R2b：脚本齐备 + 守卫计数 + ① 未采纳理由留存）；
- `LocalMySqlIntegrationTest`：迁移脚本连跑两轮幂等；「删掉索引 → 跑迁移 → 补齐」用例；并断言 `notice_record` **没有** `idx_notice_user`（防回归加回无用索引）；
- `./mvnw test`（H2）与 `./mvnw test -Dmysql.local.enabled=true`（真库）均 0 失败；
- `scripts/explain-bg2-2026-09-23.sh` 可随时重跑复现上表。

## 4. 部署提示

存量库升级**必须**执行 `db/migration-2026-09-23-perf.sql`（与其余 4 个 09-23 迁移脚本并列，见 `docs/deployment.md` §2.1）。
纯加索引、不改列与数据，对应用向后兼容；大表加索引会短暂持有 MDL，建议低峰执行。

## 5. 局限说明（不夸大）

- 本机 MySQL（Windows、非生产等价硬件、`innodb_buffer_pool` 默认）测得的**绝对值**不能作为验收数字；
  本报告只用于**同一环境下的前后对比**与优化器计划判定（走哪个索引、是否 filesort），这部分结论与硬件无关。
- B-G1 的 P95 < 500ms 压测仍未做（需生产等价环境与万行数据），见 `.project-state.md` 阻塞项；
  本报告的 ① ② ⑤ 均为单条 SQL 的计划与耗时对比，**不等于**接口级 P95 达标。
- 旧实现（内存集合差）的 Java 侧成本未单独测量，故 ⑤ 的「端到端」结论只做了定性说明（内存/查询次数），未给端到端毫秒数。
